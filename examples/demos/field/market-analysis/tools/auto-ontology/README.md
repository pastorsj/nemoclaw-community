# Auto Ontology (`ontology` profile)

NVIDIA Auto Ontology maps business terms onto database columns and answers questions with SQL. In this demo it
answers structured questions over the active data pack's DuckDB database. The agent calls one tool,
`ask_question`, which Hermes sees as `mcp__auto_ontology__ask_question`. The call returns the answer, the SQL,
the rows and the resolution lineage (which phrase mapped to which ontology object, table and column).

**Auto Ontology answers the demo's structured questions.** The `ontology` profile builds it from the public
upstream repository, `NVIDIA/auto-ontology`, checked out as a submodule; there are no published images. Replay
shows the recorded structured answers without it.

This directory holds only what we add to upstream:

| Path | What |
| --- | --- |
| `prepare.sh` | Exports the pinned commit to `.build/auto-ontology` and applies the patches |
| `patches/backend/` | Two patches to the Auto Ontology backend |
| `patches/mcp/` | One patch to the Auto Ontology MCP server |
| `seed.py` | Imports `/data/active/ontology/model.yaml` into the backend, and seeds the pack's catalog again when the model changed ([seeding](#seeding)) |

## How it fits

```text
data (one-shot) ──> /data/active/structured/<database>.duckdb, ontology/model.yaml
auto-ontology-db (pgvector) ──> auto-ontology-migrate ──> auto-ontology (backend, :3001)
                                                            ├──> auto-ontology-seed (imports model.yaml)
                                                            │      └──> auto-ontology-ingestion (:3002)
                                                            └──> auto-ontology-mcp (127.0.0.1:3003/mcp) <── Hermes
auto-ontology-db ──> auto-ontology-frontend-migrate ──> auto-ontology-frontend (web UI; the API signs in here)
```

- The images are upstream's own Dockerfiles (non-root uid 1000, tini), built from `.build/auto-ontology`. Only
  the MCP server is published, on 127.0.0.1:3003. The sandbox reaches it as `host.openshell.internal:3003`.
- The ontology is not generated by Auto Ontology's LLM compiler. `demo-data prepare` derives it from the pack
  (`data/src/demo_data/ontology.py`, with the descriptions in the pack's `ontology.yaml`). The seed imports it
  (`POST /api/model/import?replace=true&embed=true`) before ingestion first starts, so ingestion reuses the
  imported IDs. Every `up` runs the seed again; when the model changed, it seeds the catalog again
  ([seeding](#seeding)).
- Each data pack has its own `auto-ontology-db` volume (`market-demo_auto-ontology-db_<database>`). The packs
  name their tables alike, and Auto Ontology keeps term names unique, so one pack's model cannot be imported over
  another's. Switching packs starts that pack's ontology database, empty the first time; `down --volumes`
  removes every pack's.
- Ingestion catalogs every relation in the DuckDB file, including the `prediction` views that exist for Kumo.
  Patch `backend/0001` keeps them out of search.
- The database connection comes from `CONNECTION_STRINGS`, not from the catalog. As a result, upstream's
  `check_readiness` tool reports `can_execute_sql: false` even though SQL runs. Hermes enables only
  `ask_question`.
- Prediction runs on the market-analytics server (`predict_asset_outcomes`, with a [Kumo service](../../docs/kumo-service.md)).
  Auto Ontology no longer calls Kumo, and Kumo does not need `ontology`.
- The agent image includes the `auto_ontology` MCP server only when it is built with the `ontology` feature
  (see `agent/README.md`).

## Seeding

Auto Ontology's import creates what the catalog lacks and drops the semantics the model no longer names, but it
never updates an entity it already has (`_import_catalog` and `_import_terms` in upstream's
`auto_ontology/dal/model_interchange.py` create or skip). A new description of a table, column, term or
attribute in a pack's `ontology.yaml` would never reach a catalog seeded before it. So `seed.py`:

1. hashes `model.yaml` (SHA-256) and reads the hash it recorded for the model's database in
   `market_demo.ontology_seed`, a table of ours in Auto Ontology's Postgres, so it lives and goes with the pack's
   `auto-ontology-db` volume;
2. when the hashes differ and the catalog holds that database, clears it with Auto Ontology's own per-database
   reset (`auto_ontology.dal.reset.delete_all_data`: its catalog rows, its semantic rows and their embeddings);
3. imports the model, as before;
4. records the hash, only after the import succeeded, so a failed run is repeated in full by the next `up`;
5. after a reset, asks the ingestion service to catalog the database again (`POST /ingest`) if it is running;
   if not, ingestion does it when it starts, as on a fresh volume.

Only the databases the model names are reset; other databases and Auto Ontology's other data are untouched.
An unchanged model is imported again, which creates nothing. A catalog seeded before the hash was recorded (an
older deployment) has no record, so its next `up` seeds it again once. Edits made in the Auto Ontology web UI
survive until the model changes; then the pack's `ontology.yaml` wins. Drop the reset once upstream's import
updates the entities it already has.

To check what a deployment holds, compare the recorded hash with the model's:

```bash
./scripts/demo.sh logs auto-ontology-seed   # "seed: the model changed; reset the catalog of <database> ..."
docker exec market-demo-auto-ontology-db-1 psql -U auto_ontology \
  -c 'SELECT database_name, model_sha256, seeded_at FROM market_demo.ontology_seed'
docker exec market-demo-auto-ontology-1 sha256sum /data/active/ontology/model.yaml
```

## Pin

`vendor/auto-ontology` is a submodule of `https://github.com/NVIDIA/auto-ontology.git` with `update = none`. A
plain `git clone --recurse-submodules` prints "Skipping submodule" and needs no credentials, and CI checks out
no submodules. The pin is the commit this repository records: `d0ebb96f` ("Sync release/v1.0 with main (#304)",
the `release/v1.0` head on 2026-09-29). There, the backend and the MCP server are both version 1.0.0.

## Patches

Each patch applies with `git apply` in order: first `backend/`, then `mcp/`.

| Patch | Why | Remove when |
| --- | --- | --- |
| `backend/0001` Hide configured schemas from semantic search | The pack's DuckDB also has a `prediction` schema of Kumo views. `SEMANTIC_SEARCH_EXCLUDED_SCHEMAS=<database>.prediction` keeps those views from answering ordinary questions. Records with no schema identity are kept (related: #254) | Upstream can exclude schemas from search |
| `backend/0002` Report ontology resolution lineage | Adds `resolution_lineage` to chat results, for the UI's ontology explorer (#251, #256) | Upstream reports typed lineage |
| `mcp/0001` Trusted service mode and lineage | Upstream MCP accepts only per-caller OAuth, so an unattended agent cannot call it. `AUTO_ONTOLOGY_MCP_TRUSTED_SERVICE_MODE=true` calls the backend with no caller identity. `ask_question` also returns `resolution_lineage` | Upstream documents a service-to-service mode and returns lineage |

The patches replace the earlier five-patch series and the 17k-line MCP fork. The Kumo patch and the
target-database patch are gone, because Auto Ontology no longer does prediction and serves one database.

Trusted service mode is safe here only because nothing untrusted can reach the server. It listens on loopback and
the Compose network, and the backend is never published. Do not enable it anywhere else.

## Env contract

Auto Ontology reads four model settings. Every field is set explicitly. If any field is unset, upstream falls back
to built-in defaults chosen by the key prefix, which may be models the endpoint does not serve or that are end-of-life.
It also falls back to `NVIDIA_API_KEY`, which this repository never uses.

| Upstream setting | Set from |
| --- | --- |
| `REASONING_ENDPOINT` / `_API_KEY` / `_MODEL` | `INFERENCE_BASE_URL`, `INFERENCE_API_KEY`, `AUTO_ONTOLOGY_REASONING_MODEL` |
| `NON_REASONING_ENDPOINT` / `_API_KEY` / `_MODEL` | `INFERENCE_BASE_URL`, `INFERENCE_API_KEY`, `AUTO_ONTOLOGY_NON_REASONING_MODEL` |
| `EMBED_ENDPOINT` / `_API_KEY` / `_MODEL` | `RETRIEVER_BASE_URL`, `RETRIEVER_API_KEY` (empty: `INFERENCE_API_KEY`), `RETRIEVER_EMBED_MODEL` |
| `RERANK_ENDPOINT` / `_API_KEY` / `_MODEL` | `RETRIEVER_RERANK_URL` (default: the hosted NIM URL for the default model), `RETRIEVER_API_KEY` (empty: `INFERENCE_API_KEY`), `RETRIEVER_RERANK_MODEL` |

Model ids, which must match the inference endpoint. The `.env.example` defaults, for build.nvidia.com:
`AUTO_ONTOLOGY_REASONING_MODEL=nvidia/nemotron-3-super-120b-a12b` (Nemotron 3 Super) and
`AUTO_ONTOLOGY_NON_REASONING_MODEL=nvidia/nemotron-3.5-lightning-30b-a3b` (Nemotron 3.5 Lightning). On another
OpenAI-compatible endpoint, use the ids it lists for the same models.

Both are NVIDIA-hosted Nemotron models. Ids without an `openai/`, `azure/` or `aws/` prefix go through LangChain's
`ChatNVIDIA` client. Structured output through that client works with both models. Lightning on build.nvidia.com
can be slow (about 80 s in one sample); upstream's `LLM_INVOKE_TIMEOUT_S` defaults to 120.

Other settings:

| Variable | Service | Value |
| --- | --- | --- |
| `CONNECTION_STRINGS` | backend, ingestion | `duckdb:///data/active/structured/<database>.duckdb`; the `demo-data` volume is mounted read-only at `/data` |
| `SEMANTIC_SEARCH_EXCLUDED_SCHEMAS` | backend | `<database>.prediction` (patch `backend/0001`) |
| `POSTGRES_*`, `INGESTION_SERVICE_URL` | backend, ingestion, migrate, frontend | the stack's own `auto-ontology-db` (no host port) and ingestion service |
| `AUTO_ONTOLOGY_ADMIN_EMAIL`, `AUTO_ONTOLOGY_ADMIN_PASSWORD`, `AUTH_SECRET`, `APP_URL` | frontend | web UI sign-in; generate the secrets locally |
| `AUTO_ONTOLOGY_API_URL`, `AUTO_ONTOLOGY_MCP_TRUSTED_SERVICE_MODE=true` | MCP | the backend at `http://auto-ontology:3001` |
| `AUTO_ONTOLOGY_API_URL`, `AUTO_ONTOLOGY_MODEL`, `AUTO_ONTOLOGY_SEED_TIMEOUT_S` | seed | defaults: `http://auto-ontology:3001`, `/data/active/ontology/model.yaml`, `600` |
| `POSTGRES_*`, `INGESTION_SERVICE_URL`, `PYTHONPATH=/app` | seed | the backend's database and code, for the seed record and the reset; the ingestion service, to catalog a re-seeded database |

## Run

From this example's directory:

```bash
git submodule update --init --checkout vendor/auto-ontology   # update = none: must be explicit
tools/auto-ontology/prepare.sh                                # writes .build/auto-ontology
```

Then add `ontology` to `COMPOSE_PROFILES` in `.env` and start the demo with `scripts/demo.sh`. Build the agent
image with the `ontology` feature, so Hermes gets the `auto_ontology` server.

The images are built locally from the submodule; do not publish them.

## Move the pin

```bash
git -C vendor/auto-ontology fetch origin release/v1.0
git -C vendor/auto-ontology checkout --detach <commit>
git add vendor/auto-ontology
tools/auto-ontology/prepare.sh --check
```

If a patch no longer applies, reapply it by hand on an export of the new commit, regenerate it with `git diff`,
and keep its header. Delete a patch once upstream ships the same behavior.
